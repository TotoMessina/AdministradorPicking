# PickingUp Distributors API — Integration Specification & Technical Prompt

> **Audience:** Automated Code Assistants (e.g., Antigravity / Cursor / Copilot), Senior Backend Developers, and Integration Engineers.  
> **Objective:** Connect an external ERP / Management System with the PickingUp B2B Platform.

---

## 1. Executive Summary & Architecture

The PickingUp Distributors API facilitates bidirectional data synchronization between an internal ERP and the PickingUp mobile/web ordering platform.

### Source of Truth (Data Ownership)
* **ERP is the Source of Truth for:** Product Catalog, Categories, Stock, Pricing, Customers, Customer Groups, and Sellers.
* **PickingUp is the Source of Truth for:** Inbound Orders placed by customers or sales reps in the field.

### Key Architectural Guidelines
1. **External Identifiers (`code`):** The ERP primary key or SKU must be passed as `code` across all entities. Never design the ERP around internal database integer IDs generated by PickingUp.
2. **Batch / Atomic Ingestion:** Bulk endpoints accept arrays. Batch creation operations are strictly atomic: if one record is invalid, the whole batch fails.
3. **Partial Updates (PATCH):** Batch and individual `PATCH` calls only update provided fields. Omitted keys remain unchanged.
4. **Idempotency:** Endpoints are idempotent. Resending identical payloads produces identical target states.

## 2. Authentication & Base Setup

* **Base URL (Staging):** `https://mainapi-staging.pickingup.ar`
* **Base Path:** `/api/external/distributors/v1`
* **Auth Protocol:** Bearer Token via HTTP Header.

```http
Authorization: Bearer <DISTRIBUTOR_API_TOKEN>
Content-Type: application/json
Accept: application/json
```

* Unauthenticated or expired tokens return `401 Unauthorized`.
* Session verification endpoint: `GET /api/external/distributors/v1/me`.

## 3. Relational Dependency Hierarchy

To prevent foreign key constraints and validation failures, entities must be synced strictly in the following sequence:

```text
Level 1 (Independent):
  ├── Categories
  ├── Pricelists
  ├── Customer Groups
  └── Sellers

Level 2 (Depends on Level 1):
  ├── Products (requires category_code)
  └── Customers (requires pricelist_code; optionally group_code, seller_code)

Level 3 (Depends on Level 2):
  └── Pricelist Prices (requires pricelist code & product code)

Level 4 (Transactional Sync):
  └── Orders (requires Products and Customers to be pre-synchronized)
```

## 4. Endpoints & Operations Reference

### 4.1. Identity
* `GET /me` — Returns authenticated distributor profile.

### 4.2. Categories
* `GET /categories` — List all categories.
* `POST /categories` — Batch create categories.
* `PATCH /categories` — Batch update categories.
* `GET /categories/{code}` — Get single category.
* `PATCH /categories/{code}` — Update single category.
* `DELETE /categories/{code}` — Delete single category.
* `POST /categories/batch-delete` — Batch delete categories.

### 4.3. Customer Groups
* `GET /customer-groups` — List customer groups.
* `POST /customer-groups` — Atomic batch create groups.
* `PATCH /customer-groups` — Atomic batch update groups.
* `GET /customer-groups/{code}` — Get single group.
* `PATCH /customer-groups/{code}` — Update single group.
* `DELETE /customer-groups/{code}` — Delete single group.
* `POST /customer-groups/batch-delete` — Atomic batch delete groups.

### 4.4. Sellers
* `GET /sellers` — List sellers.
* `POST /sellers` — Atomic batch create sellers.
* `PATCH /sellers` — Atomic batch update sellers.
* `GET /sellers/{code}` — Get single seller.
* `PATCH /sellers/{code}` — Update single seller.
* `DELETE /sellers/{code}` — Delete single seller.
* `POST /sellers/batch-delete` — Atomic batch delete sellers.

### 4.5. Customers
* `GET /customers` — List customers.
* `POST /customers` — Atomic batch create customers.
* `PATCH /customers` — Atomic batch update customers.
* `GET /customers/{code}` — Get single customer.
* `PATCH /customers/{code}` — Update single customer.
* `DELETE /customers/{code}` — Delete single customer.
* `POST /customers/batch-delete` — Atomic batch delete customers.

### 4.6. Products
* `GET /products` — List products.
* `POST /products` — Batch create products.
* `PATCH /products` — Batch update products.
* `GET /products/{code}` — Get single product.
* `PATCH /products/{code}` — Update single product.
* `DELETE /products/{code}` — Delete single product.
* `POST /products/batch-delete` — Batch delete products.

### 4.7. Pricelists
* `GET /pricelists` — List pricelists.
* `POST /pricelists` — Batch create pricelists.
* `PATCH /pricelists` — Batch update pricelists.
* `GET /pricelists/{code}` — Get pricelist details.
* `PATCH /pricelists/{code}` — Update single pricelist.
* `DELETE /pricelists/{code}` — Delete single pricelist.
* `POST /pricelists/batch-delete` — Batch delete pricelists.

### 4.8. Pricelist Prices (Upsert Engine)
* `GET /pricelists/{code}/prices` — List all prices for a specific pricelist.
* `PUT /pricelists/{code}/prices` — Batch upsert (create or update) prices within a pricelist.

### 4.9. Orders (Fulfillment & Polling)
* `GET /orders` — List inbound orders (supports pagination and filtering).
* `GET /orders/{id}` — Get single order details with item breakdown.
* `PATCH /orders/{id}` — Update order status and acknowledgment mark.

## 6. Critical Business Rules

### 6.1. Stock Control Logic
* If `stock_control: true`:
  * `stock_available` is **mandatory**.
  * The PickingUp platform enforces inventory validation. If `stock_available <= 0`, the SKU is displayed as **"Out of Stock"** and purchases are blocked.
* If `stock_control: false`:
  * The SKU has infinite availability. `stock_available` is ignored.

### 6.2. Price Deletion Protocol
* **No `DELETE` or `POST` endpoints exist for prices.**
* All price submissions are performed through `PUT /pricelists/{code}/prices` (Upsert).
* **To delist/remove an item from a pricelist:** Submit `price: 0` (or `final_price: 0`). The platform interprets zero as **"not for sale under this pricelist"** and forbids order placement.

### 6.3. Soft Disable vs Hard Delete
* Prefer setting `"enabled": false` via `PATCH` rather than issuing `DELETE` or `/batch-delete`.
* Hard deletion of entities that are referenced in historical orders will produce integrity violations or orphan references.

## 7. The Order Polling & Sync Lifecycle (Fulfillment Pipeline)

Every integration client must execute the following state machine:

```text
       [Buyer places Order]
                 │
                 ▼
       Status: "pending"  ◄─── (ERP polling via GET /orders)
                 │
      [ERP inserts into DB]
                 │
                 ▼
       PATCH /orders/{id} ───► Status: "processing" (Ack / Exported)
                 │
    [ERP dispatches warehouse]
                 │
                 ▼
       PATCH /orders/{id} ───► Status: "shipped" / "delivered"
```

1. **Step 1: Poll.** Query `GET /api/external/distributors/v1/orders` at set intervals (e.g., every 3 to 10 minutes), filtering for unexported/pending records.
2. **Step 2: Parse & Store.** Extract `customer.code` and `items[].sku`. Match with local records and generate the internal Sales Order / Invoice.
3. **Step 3: Acknowledge (Mandatory).** Send `PATCH /api/external/distributors/v1/orders/{id}` with the updated status.  
   * *Warning:* If this acknowledgment is omitted, the order remains unmarked, resulting in duplicate ERP imports on the next execution cycle.
4. **Step 4: Status Updates.** As the order progress occurs locally (shipped, canceled, delivered), send subsequent `PATCH` requests to keep the buyer notified inside the mobile app.

## 8. Directives for Antigravity / AI Agent

When reading this specification to build the integration:
1. **Model Representation:** Create local database entities/interfaces matching the schemas above, guaranteeing that `code` maps to the local ERP primary key.
2. **Sync Jobs:** Split integration tasks into:
   * **Full Catalog Sync (Daily/Nightly):** Iterates Categories -> Products -> Pricelists -> Prices -> Customers.
   * **Stock & Price Fast Sync (Every 5-15 mins):** Dispatches modified stock levels and updated prices using `PATCH /products` and `PUT /pricelists/{code}/prices`.
   * **Order Collector Job (Every 2-5 mins):** Queries pending orders, writes them to the ERP, and calls `PATCH /orders/{id}`.
3. **Error Handling:** Ensure batch operations catch validation rejections and record un-synced entity logs for manual operator review.
